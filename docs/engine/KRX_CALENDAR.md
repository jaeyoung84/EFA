# EINT-004 — KRX 거래 세션과 추천 최신성

이 정책은 추천 게시 시의 KRX **주식** 거래일/자료 기준일을 검증한다. 주문·자동 모의체결,
시장 데이터 수집, AWS 스케줄러를 만들지 않는다. 추천 계산 결과가 실제로 최신 데이터인지
수집기와 대조하는 기능도 다음 단계다.

## 기준과 범위

패키지의 [2026 캘린더](../../engine/kqs/src/kqs_publication/calendars/krx_equity_2026.json)는
KRX의 거래일 규칙(평일, 공휴일, 근로자의 날, 연말 휴장 및 시장이 별도로 정한 휴장)을
출처로 하며, 검토한 연도별 휴장 예외를 명시한다. [KRX 거래 규칙](https://global.krx.co.kr/contents/GLB/06/0602/0602010201/GLB0602010201T1.jsp)과
[KRX 증시일정](https://global.krx.co.kr/contents/GLB/05/0501/0501060000/GLB0501060000T3.jsp)을
참조했다. 새해/임시 휴장은 새 파일·SHA·successor manifest·테스트를 추가해야 한다.
알 수 없는 연도는 평일로 추정하지 않고 게시/조회 모두 실패한다.

2026 추석의 마지막 거래일은 9월 23일, 휴장은 24·25일, 다음 거래일은 28일로 고정했다.
이 사실은 코드·회귀 테스트에 같이 기록되어 단순 월~금 계산으로 대체되지 않는다.

> **EINT-029(2026-10-06) 이후 새 게시 정책 `krx-session-expiry/v3`: 세션 자료는 같은 날 22:00 KST부터 공개된 것으로
> 보고, 게시는 다음 거래일 22:00 KST(다음 자료 공개 기대 시각)까지 유효하다 — 금요일 밤 게시가 주말을 넘어 월요일 밤
> 새 게시까지 유지된다. 24시간 상한 대신 안전 상한 10일. v2(21:30·24시간 상한, EINT-028)와 v1 게시본은 각자의
> 정책으로 계속 검증된다.**
>
> 이전 단계 기록 — **EINT-028 정책 `krx-session-expiry/v2`: 세션 자료는 같은 날 21:30 KST부터 공개된 것으로
> 본다.** 예약 실행은 22:00 → 06:00 → 08:30 KST 순서로 시도하고, 그 거래일이 게시되면 남은 시도는 KRX를 부르지 않고
> 끝난다. 21:30 역시 시스템의 기대 시각일 뿐 KRX 공개 보증이 아니다 — 자료가 아직 없으면 수집이 실패(빈 응답은 저장하지
> 않음)하고 다음 시도에서 다시 받는다. 휴장일 파일(SHA)은 바꾸지 않았고, v1으로 이미 게시된 추천은 그 metadata의 정책으로
> 계속 검증된다. v2의 만료 상한은 생성 후 24시간·다음 세션 공개 기대 시각 이전. 아래 v1 설명은 역사 기록이다.

`06:00 KST`는 **이 시스템의 보수적인 데이터 공개 기대 시각**이다(v1). KRX가 이 시각에
특정 DB/공급자를 갱신한다는 보증이 아니다. 따라서 worker는 실제 가격 DB의 기준일을
별도로 검증해야 하며, 수집 성공 증명은 하지 않는다.

## 2027 캘린더와 연도 경계 (EINT-016, 2026-09-30)

[2027 캘린더](../../engine/kqs/src/kqs_publication/calendars/krx_equity_2027.json)는 KRX 공식 2027 일정(보통 12월 공표)
**이전에 미리 만든 검토본**이다(`review_status: provisional-before-krx-official-2027-schedule`).

- 근거: KRX 휴장 규칙(평일 공휴일·대체공휴일·근로자의 날·연말 휴장) + 공휴일 계산
  `python-holidays 0.105`(KR) + 음력 교차 확인(`korean-lunar-calendar`, `pandas-market-calendars` XKRX).
- **2026년 개정법 반영**: 제헌절·노동절이 대체공휴일이 적용되는 공휴일이 됐다. 실제 2026 KRX 원본 DB에서
  2026-05-01·2026-07-17에 거래가 없음을 확인했다. 그래서 2027년 5/3(노동절 대체)·7/19(제헌절 대체)를 휴장으로 넣었다.
  `pandas-market-calendars`에는 이 두 날이 없다 — KRX 공식 일정으로 반드시 재확인한다.
- 2027 휴장 16일: 1/1, 2/8, 2/9, 3/1, 5/3, 5/5, 5/13, 7/19, 8/16, 9/14, 9/15, 9/16, 10/4, 10/11, 12/27, 12/31.
- 재확인 절차: KRX 2027 일정이 공표되면 이 파일과 비교한다. 다르면 파일을 고치지 말고 새 내용으로
  새 SHA·successor manifest·테스트를 추가해 **엔진 worker와 백엔드를 함께** 배포한다(게시 SHA와 reader SHA가 같아야 한다).
- 연도 경계: `next_session`·`latest_available_session`·`publication_window`는 인접 연도의 **검토된 파일로만** 넘어간다.
  2026-12-30 다음 세션은 2027-01-04이고, 2027-01-04 아침(1/4 자료 공개 전) 최신 세션은 2026-12-30이다.
  검토 파일이 없는 2028년으로는 넘어가지 않고 실패한다.
- 알려진 차이: 2026 캘린더 파일에는 2026-07-17(제헌절)이 빠져 있다(실제로는 휴장). 이미 지난 날짜라 운영에
  영향이 없고, 파일을 바꾸면 이미 게시된 추천의 캘린더 SHA가 달라지므로 그대로 둔다.

## 연간 자동 준비 (EINT-030)

매년 **12월 15일 09:00 KST** GitHub Actions(`.github/workflows/kqs-calendar-prepare.yml`)가 다음 해 캘린더를 준비한다.

1. `scripts/kqs_calendar_prepare.py`: 한국천문연구원 특일 정보(공공데이터포털 `getRestDeInfo`, isHoliday=Y — 주 출처)와
   python-holidays(KR, 교차 확인)로 평일 공휴일(대체·임시 포함) + 노동절 + 그해 마지막 평일을 휴장일로 만든다.
   두 출처가 다른 날짜는 휴장일로 자동 선택하지 않고 보고서·PR에 남긴다. 파일이 없으면 만들고 엔진에 등록,
   있으면(잠정본 등) 대조해 다르거나 잠정이면 갱신한다. **실행 중인 해의 파일은 바꾸지 않는다**(게시본 SHA 보호).
2. 바뀐 것이 있으면 `engine/kqs/tools/new_revision.py`로 다음 EINT 개정 기록·검증 기록을 쓰고 CHANGES 초안을 붙인 뒤,
   엔진 테스트와 `check_revision.py`를 통과해야 PR을 연다. **main에 자동 반영하지 않는다.**
3. 사람이 KRX 공식 증시 일정과 대조해 PR을 병합하면 백엔드가 배포되고, 서버 엔진 worker 이미지는 다시 빌드한다.
4. 홈페이지 알림: 12월 1일부터 내년 캘린더가 없으면, 20일부터 아직 잠정본이면 경고한다.

필요한 설정: 저장소 비밀값 `KASI_HOLIDAY_API_KEY`, 그리고 Actions가 PR을 만들 수 있게 하는 저장소 설정.
GITHUB_TOKEN으로 만든 PR에는 다른 워크플로(CI)가 자동으로 돌지 않으므로 테스트는 이 작업 안에서 돌린다.
엔진 테스트 중 '등록되지 않은 해' 검사는 등록된 마지막 해의 다음 해를 쓰도록 바꿔 새 해가 등록돼도 의미가 유지된다.

## 게시 조건

native 추천은 다음을 전부 만족해야 한다.

1. `data_as_of`가 해당 연도 검토 캘린더의 세션이다.
2. 생성 시점에 공개 기대 시각이 지난 세션 중 가장 최신 세션과 정확히 같다.
3. payload에 `calendar_id`, 설치된 캘린더 raw SHA-256, 정책 ID, 기대 시각을 남긴다.
4. 만료는 생성 후 24시간 이내이면서, 다음 세션 자료의 공개 기대 시각보다 이르다.
5. 홈페이지 reader도 같은 설치 캘린더 SHA를 재확인한다. 누락/변조/미지원 연도는 fail-closed다.

따라서 9월 28일에는 9월 23일 자료를 잠시 게시할 수 있지만, 9월 29일 06:00 KST 이후에는
9월 28일 자료가 아니면 게시할 수 없다. 이 경우도 데이터가 실제로 도착했는지는 아직
별도 collector 품질 검증이 필요하다.

EINT-003 형식의 native snapshot에는 캘린더 metadata가 없으므로 EINT-004 reader에서
의도적으로 거부된다. 안전한 재게시가 필요하지만, 이번 단계에서는 실제 snapshot을 만들거나
기존 DB를 바꾸지 않았다.

```bash
  python3 -m unittest discover -s engine/kqs/tests -p 'test_publication.py' -v
```

경계, 오래된 기준일, 만료 상한, calendar SHA 변조를 검사한다.
