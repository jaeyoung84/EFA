# 통합 엔진 재검토 — 2026-09-29

## 결론

엔진을 한 저장소에서 계속 개발하는 방향은 적합하다. 다만 기존 일일 파이프라인을
홈페이지에서 그대로 실행하면 자동 모의체결까지 활성화된다. **추천·이유 제공 → 사용자
판단 → 사용자 수동 모의매수/매도 기록**이라는 최신 요구에 맞게 실행 경계를 나눠야 한다.
이 문서는 근거 검토이며, 해당 기능 결함을 수정하거나 AWS를 배포한 결과가 아니다.

원본 코드/연구 규칙/DB/CSV는 수정하지 않았다. 운영 확인도 SQLite `mode=ro`,
기준일/건수/유무/해시 조회만 했고 연구·전향 러너·수집 API는 실행하지 않았다.

## 발견한 보완점 — 아직 미수정

### P0: 오래된 추천이 조회 때마다 유효해지는 만료 정책

외부 `kqs-bridge/recommendations.py`는 최신 감사 CSV를 읽으면서 generated_at을 현재
HTTP 조회 시각으로, expires_at을 현재+24시간으로 만든다. 옛 감사 자료도 다시 유효해 보일 수 있다.
**후속:** 실제 성공한 엔진 실행의 불변 snapshot_id/생성시각/기준 거래일/만료시각을 저장하고,
GET은 이를 읽기만 한다. 휴장일·공표 지연과 데이터 미갱신을 구분하고 stale 추천은 차단한다.

### P0: 자동 모의체결 경로를 새 추천 작업에서 제외

D-44의 daily_picks_cli 호출은 감사뿐 아니라 기존 엔진 체결 원장을 갱신한다.
**후속:** 수집→순수 스캔/선정→추천 근거 snapshot→읽기 API로 분리한다.
홈페이지 사용자 수동 원장에 엔진 자동 체결을 생성·복사·합산하지 않는다.
원래 전향 기록을 계속할지/분리 보존할지는 기존 규약과 사용자 방침을 대조해 별도 결정한다.

### P0: 학습 test 반복 평가/소진 관리 부재

`run_kqs_offline_baseline.py`는 기본 dry-run에서도 train/validation/**test**를 매번 내려받고
평가한다. 이어 `--record`로 재실행하면 같은 test를 다시 본다. "1회 보고값" 문구는 실행 제한이 아니다.
**후속:** 먼저 데이터셋과 분할을 동결하고, train/validation 실험과 최종 test 개방을 분리한다.
개방/소진·모델 artifact·코드/의존성/난수/파일 해시를 기록한다. 검토된 결과의 기록은 재학습 없이 수행한다.

### P1: 데이터셋 지문/분할의 재현성 부족

`routers/kqs.py`의 `_kqs_training_partition`은 시간순 분할과 label 경계 겹침 제거를
구현했다. 그러나 표본이 늘 때 60/20/20 경계를 다시 계산하므로 영구 고정 분할이 아니다.
지문은 결정/20일 결과 일부만 포함하고 전체 features·분할 소속·코드 버전을 포함하지 않는다.
실험 등록도 현재 **건수**만 비교하여 내용이 다른 같은 건수의 데이터를 구분하지 못한다.
**후속:** 불변 manifest ID, 완전한 특징/레이블 파일 해시, 실제 분할 소속, 준비도→export→실험
간 동일 snapshot 검증을 추가한다. 학습 주기가 바뀌어도 이미 개방한 시험 구간은 숨겨진 새 표본이 되지 않는다.

### P1: 판단 시 입력과 판단 후 정보의 혼합 위험

사용자가 판단과 함께 입력한 evidence_tags가 현재 모델 features에 들어간다.
미래 수익률을 제외한 것은 맞지만, 결정 레이블의 근거를 같은 레이블 예측의 입력으로 쓰면
추천 시점에 없던 정보가 섞일 수 있다. **후속:** recommendation-time features와 human annotations를
분리하고 시각/provenance를 기록한다. 사용자 모방 정확도는 수익성/자동매매 준비도를 의미하지 않는다.
120건 준비 기준 역시 충분한 독립 표본·시장 국면·클래스 다양성을 자동 증명하지 않는다.

### P1: 추천 이유와 버전/자료 보관 보완

- 현재 이유는 선정 상태/유동성 위주다. 규칙 ID, 실제 RSI·밴드·OBV·시장 레짐 값/기준을
  검증된 신호 계산에서 함께 저장해야 하며, 규칙과 다른 설명을 사후 생성하지 않는다.
- 전체 Git dirty만으로 추천을 거부하면 무관한 실험/문서 변경도 차단한다. Git 상태는 공시하되
  신뢰 판단은 실행 구성요소의 build/source hash와 동결 설정·데이터 snapshot으로 한다.
- raw DB/보고서/소진 구간 결과 파일은 아직 목록/해시만 있다. 원본 폐기 전 비공개 저장소에
  실제 파일 및 Git 이력을 백업하고 복구 검증해야 한다. 참조→산출물 연결도 항목별 대조가 필요하다.

## 통합 진행 순서

1. **근거 기준선 보존(이번 작업):** 원문/코드/테스트/연구/외부 러너·로그, 최신 결정 색인,
   변경 지침, 무결성 검사. 대용량·원시 데이터는 비공개 백업 후속으로 명시.
2. **실행 패키지 이전:** 보관본과 바이트 대조해 필요한 핵심 엔진을 이 저장소의 독립 package/worker로
   옮긴다. 과거 연구는 실행 대상에서 제외하고 잠금 source는 보존한다. 원본 PC/WSL을 먼저 삭제하지 않는다.
3. **읽기 전용 추천 경로:** 자동 체결을 호출하지 않는 작업과 /api/kqs/recommendations를 연결.
   규칙 근거/버전/기준일/불변 snapshot/만료 및 무신호 표시를 계약 회귀 테스트로 확인.
4. **KRX 운영 신뢰성:** 검증된 거래일 캘린더·공표 지연 정책, 단일 기록자/잠금/멱등/실패 관측.
   합성 휴장/공표지연 사례로 테스트하며 단순 평일 계산을 재사용하지 않는다.
5. **AWS PC 독립 운영:** 현행 배포 형태에 맞는 별도 worker 실행·의존성 잠금·영속 저장·비공개 백업.
   같은 저장소를 쓰되 웹 요청 프로세스에서 수집/연구를 실행하지 않는다. 운영 변경은 별도 검증/승인 후.
6. **수동 원장·학습 규약:** 엔진 관측과 별도로 수동 이벤트를 보존하고 불변 dataset/holdout
   개방 이력부터 보완한다. 그 뒤 오프라인 모델 실험으로 진행; 자동매매 활성화는 범위 밖.

합성/격리 데이터의 새 단위·회귀·계약 검증은 필요한 작업이다. 금지하는 중복은 이미 끝낸
전략 선택 실험의 반복이지, 변경으로 발생할 수 있는 새로운 버그의 검증이 아니다.
