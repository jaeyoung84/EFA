# EINT-012 — KQS 사용자 수동 원장 정합성

2026-09-30 로컬 구현·검증. 엔진 0.6.0 / EINT-007A는 변경하지 않았다.
추천은 엔진이 제시하고 매수·매도 판단과 가격·수량은 사용자가 입력한다.
주문·자동 모의체결·실제 시세 조회·AI 학습을 새로 실행하지 않는다. 별개 레버리지 DCA는 변경하지 않는다.

## 거래 시각과 기록 시각

| 항목 | 의미 |
| --- | --- |
| `recorded_at` / `decided_at` | 서버 원장 저장 시각. 새 기록은 UTC이며 Mongo 정밀도에 맞춰 밀리초로 저장한다. |
| `trade_at` | 사용자 입력 거래 시각(시간대 필수). UTC로 정규화하고 화면에는 KST로 표시한다. |
| `trade_date` | 거래일, KST 기준 날짜. 거래 시각과 함께 입력하면 두 날짜가 같아야 한다. |
| `trade_time_source` | 시각이 실제 입력인지 기본값인지 구분하는 출처. |

- `user_time`: 사용자가 거래 시각을 입력했다. 증권사 체결을 확인한 값이라는 의미는 아니다.
- `user_date_only`: 거래일만 입력했다. `trade_at: null`이며 같은 날의 거래 순서는 증명할 수 없다.
- `record_time_default`: 둘 다 입력하지 않아 기록 시각을 기본 거래 시각으로 사용했다. 실제 거래 시각으로 단정하지 않는다.
- `legacy_unspecified`: 과거 기록에 출처가 없다. 기존 DB를 덮어쓰거나 과거 시각을 추정하지 않는다.

추천 화면에 선택적 KST 거래 시각 입력을 추가했다. 보유 청산 화면은 기존 거래일 입력을 유지하고
선택적 거래 시각을 추가했다. 청산 거래일의 기본값은 오늘이며 과거 시각을 입력할 때 거래일도 맞춰야 한다.
기록 목록의 예전 시간대 없는 Mongo 시각은 UTC로 해석해 KST로 표시한다.

미래 시각·미래 거래일·추천 생성 이전의 추천 거래 기록은 거부한다.
기존 같은 종목 거래일보다 앞선 입력, 양쪽 시각이 알려진 같은 날의 역순 입력도 거부한다.
같은 날 날짜만 있는 기록이나 기존 시각 미상의 기록은 정확한 선후 관계를 검증할 수 없다.
이 기능은 거래소 영업시간/휴장일을 확인하거나 시장 체결을 보증하는 기능이 아니다.

## 요청 재시도와 새 기록

기존 API 경로를 유지한다.

- `POST /api/kqs/decisions`: 추천에 대한 매수·매도·관망·제외·재검토 판단.
- `POST /api/kqs/decisions/positions/{symbol_key}/sell`: 추천 만료 후에도 보유 lot 전량/부분 청산.

선택적 `request_id`를 양쪽 API에 추가했다. 8~128자이며 영문·숫자로 시작하고
영문·숫자·`._:-`만 허용한다. 예시(실행 지시가 아닌 요청 형식):

```json
{
  "signal_id": "현재_유효한_추천_ID",
  "decision": "buy",
  "quantity": 10,
  "fill_price": 100,
  "trade_at": "2026-09-30T10:00:00+09:00",
  "request_id": "manual-buy-unique-0001"
}
```

동일 사용자·동일 ID·정규화된 동일 입력은 최초 저장 결과를 반환한다.
추천이 만료됐거나 전량 청산 뒤 보유 lot이 없어도 이미 성공한 같은 요청의 재시도는 가능하다.
이는 새 만료 추천 거래를 허용하는 것이 아니다.
추천 유효성은 요청 중 snapshot을 읽을 때 검증한다. DB 작업 사이에 만료 경계를 통과하는 경우의
저장 직전 재검증은 이번 구현에 포함하지 않았다.
같은 ID에 다른 입력·다른 API 용도를 쓰면 409이며 기존 원장은 바꾸지 않는다.
ID는 사용자별로 분리되며 인증 없이 재생할 수 없다.

Mongo의 기본 `_id` 유일성을 활용한다. 사용자 ID와 요청 ID를 SHA-256으로 묶어
ObjectId 키를 만들고 입력 지문도 저장한다. 별도 sparse 유일 인덱스나 기존 기록 마이그레이션은 없다.
이 합성 ObjectId의 timestamp를 생성 시각으로 해석하면 안 된다. 저장 시각과 `recorded_order_us`를 사용한다.

화면은 같은 폼·같은 입력의 재시도에 같은 ID를 쓰고 저장 중 중복 제출을 막는다.
입력을 바꾸거나 추천 폼에서 **새 기록 시작**을 누르면 별도 ID를 만든다.
응답이 불확실할 때 입력을 바꾸거나 새 기록을 시작하지 말고 기존 원장을 먼저 확인한다.
보유 청산은 성공 후 새 보유 현황/폼을 읽는다.

한계: 화면 ID는 현재 폼의 메모리에만 있다. 새로고침·페이지 이동·새 탭 이후에는 자동 복원되지 않는다.
직접 API를 쓰는 클라이언트는 ID와 원래 요청을 보존해야 한다.
기존 ID 없는 클라이언트도 계속 사용할 수 있지만 재전송 중복 방지는 보장하지 않는다.
서버 저장 응답이 불명확할 때는 같은 ID로 조회/재시도해 결과를 확인하고 별도 ID로 보상 거래를 만들지 않는다.

## 동시 기록과 FIFO 원장

`kqs_manual_write_locks`의 사용자별 유일 키로 새 판단/거래 쓰기를 직렬화한다.
검증·수량 확인·저장을 한 잠금 안에서 수행한다. 동시에 들어온 다른 요청은 409이며 잠시 후 재시도할 수 있다.
기존 “먼저 저장한 뒤 초과 매도면 삭제” 경로는 새 API에서 사용하지 않는다.
성공 기록을 다른 동시 요청 때문에 소급 삭제하지 않는다.

기존 FIFO 기준은 저장 순서다. 조회 순서는 `decided_at → recorded_order_us → _id`이며,
동일 밀리초의 새 기록도 마이크로초 저장 순서를 보조값으로 유지한다.
거래 시각 입력을 이유로 과거 lot을 다시 정렬하거나 기존 학습 manifest를 수정하지 않는다.
기존 수량 불일치·서버 시계 역행은 새 거래 저장 전에 차단하고 자동 복구하지 않는다.
거래 수량은 원장 정밀도 `1e-8`보다 커야 하고 NaN/무한대/계산 overflow는 422다.

전체 사용자 거래가 10,000건에 도달하면 새 거래는 409로 중단한다.
보유 조회도 10,000건을 넘으면 부분 원장으로 잔고를 계산하지 않고 409로 중단한다.
이 상한은 대규모 원장 처리의 해결책이 아니라 보수적 안전장치다.
한도에 도달하면 청산도 추가되지 않으므로 사전에 페이지 조회/검증 또는 별도 집계 설계가 필요하다.
과거 기록을 삭제해 한도를 우회하면 안 된다.

## 잠금 장애 복구와 감사 한계

잠금에 TTL이나 자동 만료를 두지 않는다. 처리 중 잠금을 만료시키면 두 writer가 동시에 매도할 수 있기 때문이다.
정상 완료·검증 예외에는 자신이 획득한 token의 잠금만 해제한다.
프로세스 종료·DB 쓰기 응답 불확실·해제 실패로 잠금이 남으면 신규 저장이 409로 막힐 수 있다.

운영 복구는 별도 권한과 다음 확인이 필요하다. 이번 단계에서 운영 DB에는 수행하지 않았다.

1. 해당 사용자의 모든 KQS 수동 writer를 중단/차단하고 진행 중 요청이 없음을 확인한다.
2. 개인 Mongo 비공개 백업을 확인하고 잠금의 정확한 사용자 키·token·획득 시각,
   동일 요청 ID의 원장 존재 여부를 읽기 전용으로 확인한다.
3. 기존 기록이 있으면 같은 요청의 재생으로 결과를 확인한다. 기록을 삭제하거나 임의로 재삽입하지 않는다.
4. 활성 소유자가 없음을 확인한 운영자만 승인된 정확한 키와 token으로 잠금을 복구한다.
   시간 경과만으로 판단하거나 모든 잠금/원장 컬렉션을 일괄 삭제하지 않는다.
5. 원장·잠금 상태를 다시 확인한 후 writer를 재개한다.

Mongo 백업에는 원장과 요청 ID/지문도 포함해야 중복 방지가 유지된다.
잠금 컬렉션은 장애 진단 범위에 포함하되 백업에 남은 활성 잠금을 운영에 무검토 복원하면 안 된다.
잠금과 원장에는 개인 식별자가 있으므로 공개 로그/Git에 백업하지 않는다.
개인 Mongo 백업·복구 검증은 이번에 완료하지 않았다.

원장 저장 후 감사 로그가 실패해도 저장된 원장은 보존하고 성공을 반환한다.
이를 실패로 보고 새 거래를 재전송하는 오류를 줄이며 서버에 감사 실패 로그를 남긴다.
감사 쓰기는 best-effort이고 durable outbox/자동 재전송은 없다. 감사 이벤트가 누락될 수 있으며
“감사 로그까지 항상 원자적으로 저장”을 주장하지 않는다.
DB 장애로 원장 insert 또는 잠금 해제 응답이 불명확하면 실패 응답이 생길 수 있다.
요청 ID를 보존한 재시도가 필수이며 ID 없는 클라이언트의 중복 위험은 남는다.

## 새 검증과 재사용한 근거

- 백엔드 **89개 통과**: 기존 KQS 69개 + 새 원장 사례 20개, skip 0, 기존 deprecation 경고 13개.
  임시 MongoDB 7 / loopback 포트 32771 / `jy_investing_test_eint012` / tmpfs만 사용했다.
- scripts **66개 통과**, skip 0. API 대역은 새 잠금·조회·count 경로를 반영했다.
- Node 22의 수동 기록·추천·native 화면 renderer 세 검사와 strategyList 문법 검사 통과.
  네트워크 차단/읽기 전용 컨테이너이며 실제 브라우저 E2E는 아니다.
- 초기 신규 회귀에서 raw NaN/Infinity의 validation error가 JSON 응답을 깨뜨리는 오류 2건을 발견했다.
  저장 전 422를 반환하도록 고쳤고 새 소량 수량/시간 역순/10,000건 한도 사례까지 최종 통과했다.
- engine revision/초기 이관/근거 보관 무결성·릴리스 로컬 구성·공백 검사 통과.
  DCA·scheduler·기존 deploy workflow 바이트는 단계 시작 전과 같다.
